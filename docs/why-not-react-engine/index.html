为什么渲染引擎不能把 React 当「权威层」

基于 Overlay demo 契约、节点响应规则（watch / spawn）、以及蓝图「选节点开播」等能力， 逐条对比：纯 TS 引擎 + React 视图 vs 整机 React 当游戏引擎。

结论： React 的「响应式心智」要对；React 的运行时不能当玩法权威层。 正确边界是：JSON → 纯引擎求值（RNG / effects / 边 / tick / watch）→ directive → React Skin 只画画面。
要支撑的能力 逐能力对照 优缺点 推荐边界 数据流 demo 实例

1. 我们真正要支撑的能力

这些不是抽象理想，而是当前 demo / schema / 节点配置已经在要求的东西。

Overlay 包（视频上只认 overlay） OverlayNode 挂到演出节点 蓝图选节点 jumpToNode 开播 watch 数值变化 spawn 瞬态组件 + ttl submit → resolve → 边 组件事件可配（manifest） 无头单测（纯 Node vitest）

配置平面（作者）

  • ui.overlays[id]：界面包 + children
  • node.overlayNodes[]：挂哪张、贴视频哪
  • node.reactions[]：watch / shown / hidden → effect / spawn / goto
  • edges[].sourceHandle：对齐 exits / submit key

运行平面（引擎）

  • 视频时钟 → tick(ms)
  • 写屏障 → pull-diff watch
  • spawn 实例化模板，到期 removeOverlay
  • 产 directive；Player / Skin 消费

2. 逐能力对照：引擎 vs 整机 React

「整机 React」= 把 JSON 编译成 React 树，用 useState / useEffect / 组件生命周期承载玩法权威。

能力 纯引擎（现状方向） 若整机用 React 当引擎 卡点
Overlay 只上视频 expand(overlay ⊕ OverlayNode) → OverlayInstance → directive JSON → 一棵 React 树条件渲染 表面都能做；权威若进组件，配置与副作用缠在一起
蓝图选节点开播 jumpToNode(id)：重置游标、保留全局态、立刻 enter 卸载旧树 / 重挂新树 / 对齐 video.currentTime StrictMode 双挂、effect 竞态、时钟与 fiber 不同步
视频时钟驱动 onTimeUpdate → session.tick(ms) 离散推进 每帧 setState 或 effect 跟视频 批处理/并发下难保证「第 N ms 必触发」；seek 回放更难
watch 掉血→表现 写屏障 pull-diff：重读 of，比 prev，带 delta useEffect(() => …, [hp]) level vs edge、多伤害源叠加、无头无 DOM 时 effect 不跑
spawn + ttl 引擎发 renderOverlay，ttl 到期 removeOverlay setTimeout + 条件渲染列表 切节点 / seek / pause 时 timer 与视频时钟脱节
交互出边 Skin emit(key) → emitComponentEvent → reactions / handle → edge onClick 里直接改血 / navigate 玩法绑死在组件；换皮、复用 overlay、图边 SSOT 全崩
组件事件可配 manifest.events + params；节点配 reactions / 边 组件 export 回调 / Context 第二套 SSOT；编辑器下拉对不齐 JSON
无头单测 Node 里 new GraphRuntime + tick，无需 jsdom 必须挂 React + 模拟时钟 + act() 115+ 测会变慢、脆、难断言确定性
确定性 / RNG seeded RNG 在纯引擎内 effect 顺序、重渲染次数影响「何时 roll」 回放 / 复现 bug 不稳定
品类扩展
(hp→score/kills)		 实体 = 开放 attrs；watch.of / bind 换字段即可 「写个新组件就行」看起来简单 简单感来自把逻辑塞组件；图编排与测试成本转移到 JSX

3. 优缺点对照

方案 B 整机 React 当引擎

优点

  • 心智熟悉：deps / mount / unmount 人人会
  • Studio 里本来就有 React，看似「少一层」
  • 临时 UI 特效用 hooks 写得很快
  • 新人容易误以为「监听数据变化=useEffect」就够了

缺点（致命）

  • 权威态进 fiber：血量、RNG、边路由跟着渲染生命周期走
  • 蓝图 seek / 选节点播：时钟与 effect 难对齐
  • watch 变成 level-triggered 或依赖重渲染次数
  • 无头测、回放、确定性变差
  • JSON 不再是可独立求值的玩法 SSOT
  • Skin 换皮会带走玩法（副作用写在组件里）

方案 A（推荐） 引擎权威 + React 视图

优点

  • 玩法纯、可测、可 jumpToNode / 回放
  • watch = 写屏障 pull-diff，与「谁改的」无关
  • spawn/ttl 跟节点时钟同一套游标
  • Skin 仍是 React：好看、可换皮、可崩隔离
  • 编辑器与运行时共享同一份 JSON 契约
  • attrs 开放：竞技 / 格斗只换字段与 overlay，不改引擎假设

缺点（可接受）

  • 要手写一小段「响应式」原语（watch/spawn），不能直接套 React API
  • 作者要学 reactions 字段，而不是只写 JSX
  • 视图层仍要一层 Player 把 directive 映成组件
  • 调试要分清「引擎日志」vs「React DevTools」

容易混淆的一点

不是 「项目里不许用 React」。 而是 React 只许出现在呈现层（GraphPlayer / Skin / 编辑器）， 不许成为「谁扣血、走哪条边、第几毫秒开火」的权威实现。

4. 推荐边界（谁干什么）

层 技术 负责 禁止
权威模拟 GraphRuntime（纯 TS） tick、effects、RNG、边、watch、spawn、jumpToNode import react；读写 DOM；在组件里藏玩法
会话壳 GraphSession 把 directive 收成 snapshot；回灌 submit 自己 invent 玩法规则
Play 视图 React GraphPlayer 视频元素、订阅 snapshot、把 overlay 指令画出来 在 useEffect 里改实体 attrs / 跳边
Skin React 组件（如 BossHitCheer） 长相、本地 UI 态、按 inputs 画、emit(event) 扣血、goto、读全局 store 改世界
蓝图编辑 React Flow + Inspector 编 JSON；响应规则下拉引用 overlayId/childId 把运行时逻辑写进画布组件

5. 数据流（一眼看懂为什么 React 接不住权威）

blueprint.json │ ├─ ui.overlays.* ← 界面包（children / layout / 默认 params） ├─ nodes[].overlayNodes ← 挂到视频上 ├─ nodes[].reactions ← watch / shown / hidden / event … └─ edges ← sourceHandle ↔ events / emit │ ▼ GraphRuntime（纯 TS，无 React） │ enter / tick(ms) / applyEffects │ 写屏障 → checkWatch（pull-diff） │ spawn → renderOverlay(+ttl) / removeOverlay │ emitEvent → reactions / 选边 → jump/enter ▼ RuntimeDirective[] │ ▼ GraphSession.snapshot ──订阅──► GraphPlayer（React） │ ▼ Skin 组件树（React） 只读 inputs / ctx.hud 只出 emit(key)

若把中间「GraphRuntime」整段换成 React 树，箭头会变成： JSON → fiber mount → useEffect 改世界 → 再渲染。 那时 视频时钟、seek、无头测、边 SSOT 全部要重新发明一遍——而且往往发明得比现在更差。

6. 用当前 demo 形状说明（bossHitCheer）

目标能力：小怪掉血时，右上角刷出「加油，boss 扣了 X，还剩 Y」，显示 3s； 「加油」可点，点后追加传入的英雄名。组件进 overlay 目录，节点用 watch + spawn 引用。 

// 1) 界面包（ui.overlays.hitCheer）—— 组件在目录里，节点才能选到
{
  "id": "hitCheer",
  "children": [{
    "id": "banner",
    "component": "bossHitCheer",
    "params": { "heroName": "空藏" }
  }]
}

// 2) 节点响应规则（node.data.reactions）—— 编排平面，不写在 React 里
{
  "when": { "type": "watch", "of": "entity.ent-boss.attr.hp", "on": "dec" },
  "do": [{
    "kind": "spawn",
    "from": "hitCheer/banner",
    "ttlMs": 3000,
    "params": {
      "dmg":    { "expr": "abs(delta)" },
      "remain": { "expr": "entity.ent-boss.attr.hp" },
      "heroName": "空藏"
    }
  }]
}

// 3) Skin（React）—— 只负责画 + 本地点击态；不扣血、不 watch
// BossHitCheer：读 params.dmg/remain/heroName；「加油」onClick 只改本地 cheered

为什么这样对

  • 掉血无论来自哪条 effect，watch 都能抓到
  • ttl / 切节点由引擎统一收
  • 换一张皮不影响「何时刷、刷多久」
  • 同一规则可在无头测试里 tick 断言

若写成 React 引擎会怎样

  • useEffect([bossHp]) 里 setFloats —— 多源伤害难叠
  • 3s 用 setTimeout —— seek 回节点会漏清/重刷
  • 点击「加油」若直接改全局态 —— 玩法泄漏进 Skin
  • 蓝图点别的节点开播 —— 旧 effect 与 timer 残留

一句话带走

用 React 的语法糖讲故事可以；用 React 的运行时当游戏核心不行。 我们要的是「声明式响应」（watch / shown / spawn），不是「把 GameRuntime 嵌进 fiber」。 视图继续 React；权威继续纯 TS。
